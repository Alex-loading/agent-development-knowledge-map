# LLM 基础全模块知识笔记设计

## 背景与目标

`llm-01：AI、机器学习与 LLM` 已验证知识笔记模式：站内长文承担主教材职责，外部资料承担证据、交叉核验与扩展阅读职责。当前 `llm-02` 至 `llm-08` 仍使用两段式 `explanations`，学习者必须依赖大量外链才能形成完整知识体系。

本次工作把第一模块其余七节全部迁移为来源可追溯、站内可独立学习的知识笔记，并保持第一节已经验证的证据标准、数据协议、通用渲染器和阅读体验。完成后，LLM 基础八节课程在内容形态上保持一致；学习者不打开外链，也应能完成现有测验、面试短答、练习与完成标准。

## 范围与非目标

本次只修改 LLM 基础模块的知识笔记、资源证据卡、相关数据测试、维护文档和必要的数据文件组织。Agent 机制、Agent Harness、上下文/RAG/记忆模块继续使用现有 fallback，不在本次迁移范围内。

不新增 Markdown 运行时、框架、第三方依赖、构建步骤或课程专用 UI；不改写既有 quiz、面试题、实验逻辑和进度协议，除非测试证明原内容与经核验来源直接冲突。不可访问的资料不得依据标题、元数据或模型记忆补写正文。

## 章节规模与学习路径

七节笔记按主题复杂度设置阅读量，不强行等长：

| 课程 | 主题 | 目标阅读量 | 教学重点 |
| --- | --- | --- | --- |
| `llm-02` | 神经网络与反向传播 | 25–30 分钟 | 前向、损失、梯度、反向传播、优化、泛化 |
| `llm-03` | Token、Embedding 与上下文 | 25–30 分钟 | tokenizer、向量表示、位置、窗口与预算 |
| `llm-04` | Attention 与 Transformer | 30–40 分钟 | Q/K/V、缩放点积、多头、掩码、残差与完整数据流 |
| `llm-05` | 预训练、微调与对齐 | 30–40 分钟 | 预训练、SFT、偏好优化、LoRA、RAG/微调决策 |
| `llm-06` | 推理、采样与 KV Cache | 30–40 分钟 | logits、temperature、top-p、prefill/decode、缓存与服务权衡 |
| `llm-07` | Prompt 与结构化输出 | 35–40 分钟 | 指令边界、few-shot、Schema、校验、有限重试与降级 |
| `llm-08` | 能力边界、评测与安全 | 30–40 分钟 | 失败分类、离线/在线评测、注入防御、质量/成本/延迟门槛 |

阅读量允许按实际复杂度浮动。`llm-07` 在复审后需要同时保留完整 JSON Schema、三组可由规则推导的样例、category/priority 业务策略及逐分支控制流，因此采用 35–40 分钟区间，不以压缩必要工程闭环来维持原先的短篇幅。

每节包含 5–7 个实质章节。章节从先修桥接与直觉模型推进到准确机制、工程意义和贯穿案例，再以常见误区、回顾和下一课连接收束。每节至少包含一个可复用工程案例，案例必须直接连接现有 exercise 与 deliverable，而不是额外增加无关练习。

正文必须覆盖该 lesson 的全部 objectives、concepts、两道 quiz、三道面试题及其追问、exercise、deliverable 和 completion criteria。章节之间需要显式分工，避免在 Token、Attention、推理和长上下文等相邻主题中重复大段定义。

## 来源与证据策略

制作每节笔记时必须调用项目 `.agents/skills/build-learning-module-notes/`。先读取 lesson 事实和全部关联资源，再逐来源访问正文，建立来源卡和覆盖矩阵，最后按知识依赖写作，禁止按链接顺序拼接摘要。

来源卡继续使用：

```text
authority: official | academic | expert | community
role: core | cross-check | extension
```

关键机制优先由官方文档、原始论文或权威教材支撑；教程用于解释和交叉核验。无字幕视频、失效页面、仅有元数据的资源只能作为 extension。版本相关实现语义记录核验日期和适用边界；资料冲突必须显式保留，不静默选择更顺耳的说法。

本次复核 LLM 模块全部 28 份资源的 evidence card。只有实际重新访问正文的资源才更新 `verifiedAt`。若一项关键结论没有可访问来源，则更换可核验来源或缩小结论；不能以课程字段、资源标题或模型记忆代替证据。

每个实质章节绑定可解析的 `sourceIds`。单节最终质量量表必须达到 85/100，且不存在断裂引用，才可接入课程数据。

## 数据与文件结构

现有 `Lesson.knowledgeNote` 和 `Resource.evidence` 协议保持不变。为避免八篇长文集中在一个文件，内容拆为：

```text
src/data/llm-foundation-notes/
  llm-01.js
  llm-02.js
  llm-03.js
  llm-04.js
  llm-05.js
  llm-06.js
  llm-07.js
  llm-08.js
src/data/llm-foundation-notes.js
```

`src/data/llm-foundation-notes.js` 保持原有公共导入路径，只负责汇总八篇笔记并递归冻结。第一节现有数据迁入 `llm-01.js`，不改变内容语义。其余模块仍可缺少 `knowledgeNote`，并继续由通用课程 renderer 回退到 `explanations`。

知识笔记文件只导出纯数据，不含 HTML、DOM 操作、事件或远端请求。通用 renderer 不按 lesson ID 分支；除非验收发现真实通用缺陷，本次不修改其视觉结构。

## 子代理生产与审查流程

工作分成两轮，最终进入同一个分支和 PR：

1. 第一轮处理 `llm-02` 至 `llm-04`：神经网络、表示、Transformer。
2. 第二轮处理 `llm-05` 至 `llm-08`：后训练、推理、Prompt、评测安全。

每轮由子代理承担边界清晰的研究与草拟任务；不同代理不得同时编辑同一笔记文件或资源注册表。主代理读取并执行项目 Skill，统一来源政策、数据契约和质量量表。起草完成后，由未参与该节写作的代理做规格审查和内容质量审查，检查事实边界、覆盖矩阵、重复、篇幅与引用。主代理负责跨课术语一致性、相邻章节衔接、资源证据卡合并与最终代码集成。

子代理报告不能替代验证。每一轮集成后必须由主代理检查实际文件、运行数据测试并核对来源引用；最终以完整测试套件和真实浏览器结果为准。

## 测试与失败处理

数据测试先从“只有 `llm-01` 有笔记”的试点契约改为完整模块契约，再实现正文。测试至少验证：

- LLM 基础恰好八节知识笔记，lesson ID 与笔记入口一一对应；
- 每节 `readingMinutes` 为 20–40、实质章节为 5–7、章节 ID 在本节内唯一；
- 每节正文达到与阅读量相称的最低长度，并包含导语、误区、回顾和下一课连接；
- 所有 `sourceIds` 可解析到本课程资源，所有 lesson 关联资源都有完整 evidence card；
- 八篇笔记及课程导出保持递归不可变；
- Agent、Harness、Context 模块仍使用 fallback，通用 UI 不硬编码 LLM lesson ID；
- DOM 安全、外链 HTTPS/`noopener noreferrer`、键盘目录、移动端 320/390px 和可见内容契约继续通过。

若来源不可访问，记录失败并降级其角色；若仍有其他来源支撑核心机制，继续制作。若关键事实无法获得足够证据，或单节质量低于 85 分，则该节保持未发布状态并继续研究，不能通过降低测试门槛或删除引用绕过。七节全部通过前不创建最终 PR。

## 验收与部署

发布前运行完整 `npm test`、全部源码 `node --check`、`git diff --check` 和工作树检查。真实浏览器在桌面和 390px 视口逐节验证八篇笔记可访问、目录可聚焦、来源链接安全、无横向溢出、控制台无错误；再抽查其他三个模块的 fallback 未回归。

最终只创建一个 PR。PR 合并到最新 `main` 后，现有 GitHub Pages 从仓库根目录自动部署。部署完成的判据是：Pages 构建状态为 `built` 且对应合并提交，公开首页可访问，`llm-01` 至 `llm-08` 的线上路由均渲染知识笔记，第四模块仍可访问，浏览器控制台无错误。
